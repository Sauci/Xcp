# SP4b — Clear and Program, Absolute Access Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an XCP master erase and program non-volatile memory — the slice where flash contents actually change, and where `CONNECT` may finally advertise flash programming truthfully.

**Architecture:** `PROGRAM_CLEAR` and each completed `PROGRAM` block defer through SP4a's pending-command machinery unchanged. Master block mode accumulates a block's payload in a module-owned buffer as frames arrive — intermediate frames answer nothing and complete in receive context — so one deferred flash write serves the whole block and no frame ever races a pending write.

**Tech Stack:** C (AUTOSAR-style BSW), Jinja2 code generation via `bsw_code_gen`, pytest + CFFI compiling the real sources, all inside `xcp-test:local` under Docker.

**Spec:** `docs/superpowers/specs/2026-09-07-xcp-pgm-sp4b-design.md` — DD62 through DD69. Read it alongside this plan; where they disagree, the spec wins and the disagreement is a defect in this plan worth reporting.

## Global Constraints

- **A build with `XCP_FLASH_PROGRAMMING_ENABLED` off must stay byte-for-byte identical to SP4a's.** Everything new lives inside that guard, including any `Xcp_CTOErrorMatrix` row you change — SP4a established the `#if`/`#else`-around-the-row pattern for exactly this.
- **The integrator callback contract is polled and identical to SP4a's three:** `E_NOT_OK` means unfinished and `*pStatusCode` is **not read**; `E_OK` means finished, successfully or not, with the outcome in `*pStatusCode`. The first call happens in the handler, so an integrator that finishes immediately is answered on the same exchange with no deferral and no `EV_CMD_PENDING`.
- **Intermediate `PROGRAM_NEXT` frames must never reach the pending-command slot.** They set `*responseExpected = FALSE`, copy their bytes, and return. If one triggered a deferred write, the next frame — paced only by `MIN_ST_PGM` — would meet SP4a's `ERR_CMD_BUSY` guard and break the sequence. DD63.
- **The MTA advances only on a successful write.** DD66. A failed write must leave it where the master left it.
- **Declare new integrator callbacks in `interface/Xcp.h` ONLY.** `interface/Xcp.h` includes `test/stub/Xcp_MemoryAccess.h`, so a declaration in both is rejected by cffi as `FFIError: multiple declarations`.
- **No test may read `Xcp_Internal`** — `test/conftest.py` builds its cdef from `interface/Xcp.h` alone. Observe through consequences; `test/clear_daq_list_test.py:80-92` is the precedent. Never add a test-only accessor to a public header.
- **SP4a's protection refusal stays.** `apis.resource_protection.programming` remains refused at generation. Only the per-command terms of the *other* refusal lift, and only as each command lands.
- Citations are to **XCP Part 2 Protocol Layer Specification 1.1** unless they name 1.0, qualified `1.1/...`. **The PGM error matrix is §1.7.3.2.5** — §1.7.3.2.4 is DAQ's, and SP4a cited it wrongly three times before its final review caught it.
- `raise(...)` is **not** a registered Jinja global; referencing it aborts rendering with `UndefinedError`. Guard tests assert generation *fails*, never that a message matches.
- **Every new test is mutation-verified**: break the term it targets, confirm that test fails and others do not, restore, confirm `git diff` is clean. A compound condition needs a test per **term**, not per outcome.

### The six ways a test here has already passed while pinning nothing

SP4a shipped six of these and every one was caught in review. They all apply:

1. Asserting on `handle.can_if_transmit.call_args` without `reset_mock()` first — reading a **stale response** from an earlier exchange.
2. Asserting after only `Xcp_CanIfRxIndication`, **which never transmits** (`Xcp_StartNextTransmission` is called from `source/Xcp.c:1327` and `:1732` only) — making the assertion unconditionally true.
3. Scanning `call_args_list` retrospectively — `Xcp_Internal.event.pdu_info` is **one buffer reused across all event types**, so older entries show whatever the *latest* event wrote.
4. A setup guard satisfied by a leftover `CONNECT` response.
5. A deferral test discarding the very value it meant to check.
6. `exchange()`-style helpers that read `call_args` without resetting.

**Block mode is more exposed than any of these**, because intermediate frames transmit *nothing at all*: `transmitted(handle) is None` after a frame is true whatever the module did with the bytes. **Every block test must assert on the bytes the integrator was handed**, not on the absence of a frame.

## How to run the tests

**`./test.sh` from the repo root is the only authoritative full run.** Run it once, at the end, in the foreground, with `XCP_PYTEST_ARGS` cleared:

```bash
docker run --rm --volume "$(pwd):/usr/project" --workdir /usr/project xcp-test:local sh -c 'cd /usr/project/build && cmake .. -DXCP_ENABLE_TEST=ON -DXCP_PYTEST_ARGS= >/dev/null 2>&1; cd /usr/project && ./test.sh'
```

`test.sh` prunes stale `_cffi_xcp_*` and `libcffi_xcp_rt_*.so` directories. **Skipping that prune produces spurious "conflicting types for 'Xcp'" compile failures that look exactly like regressions** — it has cost this project real time twice. `XCP_PYTEST_ARGS` is a CMake *cache* variable, so a stale filter makes a "full" run report green having executed almost nothing.

Filtered, while iterating:

```bash
docker run --rm --volume "$(pwd):/usr/project" --workdir /usr/project xcp-test:local sh -c 'cd /usr/project/build && cmake .. -DXCP_ENABLE_TEST=ON "-DXCP_PYTEST_ARGS=-k;pgm;--maxfail=99" >/dev/null && make all >/dev/null 2>&1 && LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/usr/project/build ctest -V --no-tests=error 2>&1 | grep -E "FAILED|passed|failed"'
```

**Never run `rm -rf generated/*`** — that directory holds build artefacts *and* the tracked `generated/CMakeLists.txt`; deleting it breaks the CMake configure and dirties the repo. **Never launch a test run in the background and wait on it** — a run that outlives your turn is lost. If Docker leaves root-owned files in `build/`, reclaim them with a rootful container running `chown -R`.

**Baseline: 12801 passed, 29 skipped, 0 failed.** Measure it once before changing anything rather than trusting this number.

## Task 1: `MAX_BS_PGM` and the block buffer

Delivers DD62. No new command, so nothing becomes advertisable — the deliverable is that `PROGRAM_START` reports a value the module can honour and the buffer exists for Task 4.

**Files:**
- Modify: `script/header_cfg.h.jinja2`, `config/xcp.schema.json`, `config/xcp.json`, `test/parameter.py`, `source/Xcp_Internal.h`, `source/Xcp_Pgm.c:389`
- Test: `test/pgm_deferred_test.py` (the existing `MAX_BS_PGM` assertion changes)

**Interfaces:**
- Produces: `XCP_PGM_MAX_BLOCK_SIZE`, the configuration key `programming.max_block_size`, and `Xcp_Internal.pgm_block` — a buffer of `XCP_PGM_MAX_BLOCK_SIZE * (XCP_MAX_CTO - 2)` bytes plus a fill level. Tasks 3 and 4 consume both.

- [ ] **Step 1: Record the baseline.** Run `./test.sh` once. Every later no-regression claim measures against that number, not against this plan's.

- [ ] **Step 2: Write the failing test.** `PROGRAM_START`'s response byte 4 must report `programming.max_block_size`, not `max_bs`. Extend `test/pgm_deferred_test.py`'s existing `test_the_positive_response_reports_the_live_communication_parameters` — or split it, since byte 4 is no longer "live". Configure `max_bs` and `max_block_size` to **different** values, so the test distinguishes them; with equal values it would pass either way, which is failure mode 5 from the list above.

- [ ] **Step 3: Run it; watch it fail** on byte 4 reporting `max_bs`.

- [ ] **Step 4: Add the configuration.** `programming.max_block_size` beside `programming.enabled`, defaulting to `8`, with a schema entry giving its range. `test/parameter.py`'s `DefaultConfig` must accept it.

- [ ] **Step 5: Generate two macros.** `header_cfg.h.jinja2` emits `XCP_MAX_DTO` but **no `XCP_MAX_CTO`** — verified, it does not exist — and the buffer needs it. Add one first, mirroring `XCP_MAX_DTO`'s existing block at `script/header_cfg.h.jinja2:54-60` exactly: same `#ifndef`/`#define`/`#endif` shape, same largest-across-configurations rule, `configuration.protocol_layer.max_cto` as the source. Then, beside `XCP_FLASH_PROGRAMMING_ENABLED` and in the same shape:

```jinja
{%- set pgm_block = namespace(size=0) %}
{%- for configuration in configurations %}
{%- if (configuration.programming.max_block_size | default(8)) > pgm_block.size %}
{%- set pgm_block.size = configuration.programming.max_block_size | default(8) %}
{%- endif %}
{%- endfor %}
#ifndef XCP_PGM_MAX_BLOCK_SIZE

/* The largest across every configuration, as XCP_MAX_DTO above is: the sources are compiled once
 * for all of them, so the buffer must hold the biggest block any of them can ask for. Reported as
 * MAX_BS_PGM by PROGRAM_START (DD62), which is what makes it the contract the master programs
 * against rather than an internal limit. */
#define XCP_PGM_MAX_BLOCK_SIZE ({{ pgm_block.size }}u)

#endif /* #ifndef XCP_PGM_MAX_BLOCK_SIZE */
```

- [ ] **Step 6: Add the buffer** to `Xcp_InternalType`, inside the existing `#if (XCP_FLASH_PROGRAMMING_ENABLED == STD_ON)` block:

```c
    /**
     * @brief One master block mode block of PROGRAM data, accumulated as frames arrive.
     * @details DD63. Intermediate PROGRAM_NEXT frames copy here and answer nothing; the frame that
     * completes the block is what calls the integrator, once, through pending_command. Sized from
     * XCP_PGM_MAX_BLOCK_SIZE, the same constant PROGRAM_START reports as MAX_BS_PGM, so the value
     * the master programs against and the space actually available cannot drift apart.
     */
    struct {
        uint8 data[XCP_PGM_MAX_BLOCK_SIZE * (XCP_MAX_CTO - 0x02u)];
        uint16 length;
    } pgm_block;
```

`XCP_MAX_CTO` is the macro Step 5 adds; do not re-derive the value here. `Xcp_Init` must zero `length` — SP3 and SP4a both shipped a defect that was exactly this omission.

Note the buffer is sized on the **largest** `max_cto` across configurations while `MAX_BS_PGM` is reported per-run, so on a multi-configuration build the buffer is at least as large as any block that can be requested. That is deliberate over-allocation, not a bug: the sources are compiled once for every configuration, so a single buffer must serve the worst case.

- [ ] **Step 7: Report it.** `source/Xcp_Pgm.c:389` changes from `Xcp_Ptr->general->maxBS` to `XCP_PGM_MAX_BLOCK_SIZE`. Leave bytes 5 and 6 alone — DD62 changes only `MAX_BS_PGM`.

- [ ] **Step 8: Run; pass. Step 9: mutation-verify** — revert byte 4 to `maxBS` and confirm exactly the new test fails.

- [ ] **Step 10: Full suite via `./test.sh`, then commit.**

## Task 2: `PROGRAM_CLEAR`

**Files:** modify `source/Xcp_Pgm.c`, `source/Xcp_Internal.h`, `source/Xcp.c`, `interface/Xcp.h`, `script/source_cfg.c.jinja2`, `config/xcp.json`; create `test/pgm_clear_test.py`.

**Interfaces:**
- Consumes: SP4a's pending-command machinery and `pgm_state`.
- Produces: `uint8 Xcp_DTOCmdPgmProgramClear(boolean *, const PduInfoType *)`, `Std_ReturnType Xcp_ProgramClear(void *address, uint32 clearRange, uint8 *pStatusCode)`, and one `case` in each of the two switches.

- [ ] **Step 1: Write the failing tests.** `PROGRAM_CLEAR` is `0xD1`, mode byte, WORD reserved, DWORD clear range — 8 bytes. At minimum:

- It is refused `ERR_SEQUENCE` (0x29) before `PROGRAM_START` succeeds — SP4a's gate, tested against a real handler for the first time.
- Inside a session it passes the current MTA and the DWORD clear range to `Xcp_ProgramClear`, and defers when the integrator is busy.
- Mode byte `0x01` is refused `ERR_OUT_OF_RANGE` (0x22) — DD67. Assert the integrator was **not** called, not merely that the answer was an error: a handler that cleared first and refused afterwards would pass a wire-only assertion.
- A non-zero `pStatusCode` yields `ERR_GENERIC` (0x31).
- Below eight bytes: `ERR_CMD_SYNTAX` (0x21).

- [ ] **Step 2: Run; fail. Step 3: Declare the callback** in `interface/Xcp.h` only, with a `@details` naming `Xcp_StoreCalibrationDataToNonVolatileMemory` whose contract it copies, and register the mock in `test/conftest.py` — SP4a's `xcp_program_prepare` is the precedent, and omitting it makes every PGM-enabled test crash in the constructor.

- [ ] **Step 4: Implement**, adding one `case` to each switch. `Xcp_ProgramClear` takes the address and range on every call, as `Xcp_ProgramPrepare` does — read `Xcp_Pgm.c`'s existing `PROGRAM_PREPARE` case for the pattern, including why the MTA is re-read from `Xcp_Internal.memory_transfer.address` rather than copied. The clear range goes in `pending_command`, which means widening its payload: it currently holds a flat `program_prepare_code_size` (`source/Xcp_Internal.h:446`). **Make it a union keyed by `pid`**, which SP4a's final review anticipated; a second flat field invites a third.

- [ ] **Step 5: Lift its refusal term.** Delete `xcp_program_clear_api_enable` from the guard in `script/source_cfg.c.jinja2` and set the key `true` in `config/xcp.json`. The other two terms stay until Task 3.

- [ ] **Step 6: Run; pass. Step 7: mutation-verify** each new term. **Step 8: `./test.sh`; commit.**

## Task 3: `PROGRAM` without block mode, and `PROGRAM_MAX`

The task that makes `CONNECT` honest — after it, all three commands the resource bit reads exist.

**Files:** modify `source/Xcp_Pgm.c`, `source/Xcp_Internal.h`, `source/Xcp.c`, `interface/Xcp.h`, `script/source_cfg.c.jinja2`, `config/xcp.json`, `test/connect_test.py`, `test/pgm_configuration_test.py`; create `test/pgm_program_test.py`.

**Interfaces:**
- Produces: `Xcp_DTOCmdPgmProgram`, `Xcp_DTOCmdPgmProgramMax`, and `Std_ReturnType Xcp_ProgramWrite(void *address, const uint8 *pData, uint16 length, uint8 *pStatusCode)`. Task 4 extends `PROGRAM` with block mode; the callback does not change.

- [ ] **Step 1: Write the failing tests.** `PROGRAM` is `0xD0`, element count, alignment for AG > 1, then data. `PROGRAM_MAX` is `0xC9` with no count — a fixed `MAX_CTO - 1` elements. At minimum:

- A single-frame `PROGRAM` hands exactly its payload bytes to `Xcp_ProgramWrite`, at the MTA. **Assert on the bytes the integrator received**, not on the response.
- The MTA post-increments by the bytes written (DD66), asserted through a following `PROGRAM` landing at the next address.
- **A failed write leaves the MTA unmoved** (DD66) — the same assertion with a non-zero `pStatusCode`, and the second `PROGRAM` landing at the *same* address. This is the term most likely to be missing, because the happy path passes without it.
- `PROGRAM` with zero elements ends the segment and answers, without calling the integrator (DD64).
- `PROGRAM_MAX` programs `MAX_CTO - 1` elements from the MTA.
- Both are refused `ERR_SEQUENCE` before `PROGRAM_START`.

- [ ] **Step 2: Run; fail. Step 3: Implement.** Both defer through the pending slot; the payload is copied into `pgm_block` even in the single-frame case, so Task 4 changes only how many frames contribute.

- [ ] **Step 4: Lift the remaining two refusal terms**, set both keys `true`, and **restore DD60's per-conjunct `CONNECT` sweep** — SP4a's §9 criterion 6 recorded it as unmeetable and this is where it becomes meetable again. One case per conjunct, not per outcome.

- [ ] **Step 5: Run; pass. Step 6: mutation-verify**, including that the MTA-unmoved test fails if the failure path advances it. **Step 7: `./test.sh`; commit.**

## Task 4: `PROGRAM_NEXT` and master block mode

**Files:** modify `source/Xcp_Pgm.c`, `source/Xcp.c`, `script/source_cfg.c.jinja2`; extend `test/pgm_program_test.py`.

**Interfaces:** produces `Xcp_DTOCmdPgmProgramNext`; `Xcp_PIDTable[0xCA]`. No new callback.

- [ ] **Step 1: Write the failing tests.** DD63 is the whole task, and its tests are the ones most able to pass while pinning nothing:

- **The buffer accumulates.** A three-frame block reaches `Xcp_ProgramWrite` as one contiguous write of the concatenated bytes, at one address. Assert the concatenation, not the call count.
- **Intermediate frames answer nothing** — but assert this by pumping `Xcp_MainFunction()` and checking no CTO frame went out, never by `transmitted(handle) is None` alone, which is true whatever the module did.
- **The integrator is called once per block**, not once per frame.
- `PROGRAM_NEXT` with the wrong element count returns `ERR_SEQUENCE` **carrying the expected count in byte 2** — assert that byte. `Xcp_FillErrorPacketWithData` and `Xcp_DTOCmdCalDownloadNext` are the precedent.
- A block declared longer than the buffer is refused `ERR_MEMORY_OVERFLOW` (0x30) and writes nothing.
- `PROGRAM_MAX` inside an open block is refused `ERR_SEQUENCE` (DD65).
- A short final frame completes the block and writes the true length.

- [ ] **Step 2: Run; fail. Step 3: Implement**, reusing `Xcp_Internal.block_transfer`'s `requested_elements` and `frame_elements` (`source/Xcp_Internal.h:391-392`). A failed block is discarded rather than resumed — §1.7.3.2.5 gives `PROGRAM_NEXT` the pre-action `SYNCH+PROGRAM`, so the master restarts from `PROGRAM`.

- [ ] **Step 4: Run; pass. Step 5: mutation-verify** — in particular, make the buffer keep only the last frame and confirm the accumulation test fails. **Step 6: `./test.sh`; commit.**

## Task 5: `GET_PGM_PROCESSOR_INFO`

Last, deliberately: DD61 kept it out of SP4a because §1.6.5.2.1's table forbids reporting both mode bits clear, and it can only be answered honestly once absolute-mode programming works.

**Files:** modify `source/Xcp_Pgm.c`, `source/Xcp.c`, `script/source_cfg.c.jinja2`; extend `test/pgm_configuration_test.py` or create `test/pgm_processor_info_test.py`.

- [ ] **Step 1: Write the failing tests.** Response is PID, `PGM_PROPERTIES`, `MAX_SECTOR`.

- `PGM_PROPERTIES` bit 0 (`ABSOLUTE_MODE`) set, bit 1 (`FUNCTIONAL_MODE`) clear — §1.6.5.2.1's `0 1`, "Only Absolute mode supported". Assert the whole byte, not just bit 0: compression, encryption and non-sequential programming must all read unsupported.
- `MAX_SECTOR` is 0 (DD68).
- Pin that the advertised mode matches reality — a `PROGRAM_CLEAR` with mode `0x01` is refused, which is what `FUNCTIONAL_MODE` clear promises.

- [ ] **Step 2: Run; fail. Step 3: Implement.** No callback and no deferral — it reports generated configuration. **Step 4: run; pass. Step 5: mutation-verify. Step 6: `./test.sh`; commit.**
